# EMAIL_DESIGN_SYSTEM — CRM / Учи.ру

**Версия 0.1.** Извлечено из CRM-гайда `Гайд CRM` (Figma, GUIDE), дополнено принципами сборки, явно обозначенными как практические. Точные компоненты и их свойства проверять в Figma: этот файл не заменяет мастер-библиотеку.

## 1. Размеры и сетка

- **Desktop:** ширина письма **680 px**; в гайде показана 4-колоночная схема.
- **Mobile:** ширина **414 px**; предусмотрена 2-колоночная схема для компактных элементов, но в самом письме предпочтительна одна колонка.
- Мобильные контентные блоки располагаются с **боковыми отступами по 16 px**. Не путать с внутренними отступами вложенных карточек.
- В примерах десктопного контента встречаются внутренние поля **24 px**, а мобильного — композиционные отступы 16 и 24 px. **Не объявлять все расстояния универсальными**: использовать соответствующий компонент, а схему spacing сверять по конкретному узлу.

## 2. Типографика

- **Oceanic Grotesk Condensed** — акцидентный шрифт для заголовков и баннерных элементов. Допускается фирменный приём выделения хайлайтером в рамках гайда.
- **Arial** — заголовки и наборный текст (Regular, Medium, Bold согласно оформлению).
- В гайде представлены типографические ступени; например, на desktop показаны **48/40, 36/36, 24/28, 16/24, 14/18, 12/16, 10/16** (кегль/межстрочный, px); на mobile — **36/32, 24/24, 24/28, 16/24, 14/18, 12/16, 10/14**. **Не устанавливать соответствие H1/H2/Body по этому перечню автоматически**: брать стиль конкретного текстового компонента.
- Длинный заголовок не компенсировать неконтролируемым уменьшением кегля; сначала изменить перенос/раскладку в пределах предусмотренного варианта.

## 3. Цвет и сегменты

- Приоритетные брендовые цвета писем — фиолетовый и коралловый; хедер/первый экран предпочтительно базовой палитры.
- Не использовать чистый чёрный для текста: выбирать разрешённый тёмно-фиолетовый по применимой палитре.
- Предпочитать читаемые дуотонные сочетания, допускаемые гайдом.
- Родители: яркие контрастные сочетания основных/дополнительных цветов; спокойные оттенки в поддержке.
- Учителя: преимущественно пастельные фиолетовые и коралловые сочетания; яркие оттенки — акцентно.
- Для новой аудитории — преимущественно основные цвета; для знакомой с брендом допускается больше дополнительных.
- Использовать Variables, алиасы и режим аудитории из `COLOR_SYSTEM.md`. **Связь токена и его слоя проверять семантически.**

## 4. Модульная сборка

- Система шаблонов **вариативная**, блоки допускают минимальную и максимальную наполненность, если это предусмотрено компонентом.
- Обязательны **хедер и футер**, даже для короткого письма. Если есть целевое действие, обязательна CTA.
- Минимум: хедер + один самостоятельный контентный блок + футер.
- Расширенный пример: хедер + один hero + **до 5–6** контентных блоков + финальный CTA + футер.
- **Один hero-блок на письмо.** Чередовать выразительные блоки с нейтральными. Не дублировать функционально одинаковые блоки.
- Поддерживать структуру: вступление → основное содержание → основное действие. Основной CTA должен вести к одной главной цели.
- В библиотеке встречаются блоки: хедеры (включая кобрендинг), футеры, hero, карточки, текстовые композиции, текст+изображение, CTA, специальные секции. Их свойства и варианты брать из Figma.

## 5. Кнопки

- **Главный CTA — коралловый**, с учётом читаемости. При необходимости кнопка может включать иконку.
- **Вторичный CTA** — пастельная версия или обводка в зависимости от фона; ориентироваться на утверждённый компонент.
- Не растягивать кнопки на всю ширину мобильной карточки: ширина по тексту с внутренними отступами.
- Если две кнопки — на mobile располагать друг под другом: сначала основная, затем дополнительная.
- В библиотеке встречаются варианты с одной, двумя и тремя кнопками; в описании секции CTA указан максимум **три кнопки в блоке**. Не трактовать это как разрешение добавлять три CTA без смысловой необходимости.

## 6. Фирменные графические приёмы

- Подтверждены паттерны, фрагменты Гриши, шипы, чешуйки; применять по актуальному визуальному гайду, а не приблизительно воспроизводить.
- **Не ставить рядом две карточки с одинаковым узором чешуек.**
- Выразительный образ Гриши требует аудиторной адаптации: подходящее мастер-бренду решение может оказаться слишком активным для учителей.
- Контентные карточки могут иметь изображения на всю область либо обтравленный объект — при наличии утверждённого варианта.
- Цвет хедера рекомендуется адаптировать к Hero, чтобы письмо не выглядело набором несвязанных цветных блоков.

## 7. Mobile: перестройка, не уменьшение

- Предпочтительна одна колонка. Две — только для компактных карточек. Более двух — не использовать.
- Порядок элементов в mobile: сверху вниз в том порядке, в котором на desktop они идут слева направо.
- Не задавать фиксированную высоту для динамических текстовых блоков; не выравнивать пробелами и пустыми строками.
- Не допускать горизонтального скролла, обрезки, наложений.
- Изображения пропорционально масштабировать или использовать предусмотренный мобильный кроп.
- Таблицы в несколько колонок превращать в карточки/списки.
- Декор можно скрывать, важный контент и CTA — нельзя.
- Отдельную мобильную реализацию блока применять только если обычная перестройка невозможна; это увеличивает вес HTML-письма.

## 8. Тёмная тема и технические ограничения для дизайна

- Почтовые клиенты могут менять HTML-фон и текст, но обычно не перекрашивают пиксели внутри PNG/JPG/GIF; проверять стыки изображений и фона.
- Не использовать светло-серый текст на светлом фоне; сохранять контраст текста и кнопок.
- Значимые данные (дата, условия, заголовок, CTA) должны существовать текстом, а не только внутри картинки; смысловым изображениям нужен alt.
- Тёмным логотипам и иконкам может понадобиться плашка.
- Изображения: JPG — фото; PNG — графика с прозрачностью/иконки/логотипы; GIF — простая анимация. SVG для массовых рассылок не рекомендуется без гарантированного fallback.
- PNG иконок/логотипов рекомендован к экспорту в 2×. GIF должен передавать смысл с первого кадра, CTA нельзя прятать внутрь GIF.
- Это **проектные ограничения**, а не доказательство реальной совместимости: внешний HTML требует QA в почтовых клиентах.

## 9. Что не зафиксировано численно

Полный набор параметров каждого варианта компонента, правила привязки каждого конкретного слоя к Variables, допустимые эффекты в отдельных шаблонах — определять по живой компонентной библиотеке, не изобретать.
